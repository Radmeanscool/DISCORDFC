# Technical Gameplay State Matrix — DISCORDFC

**Tanggal:** 26 Agustus 2026  
**Tujuan:** Menetapkan model state dan urutan gameplay yang dapat dipertanggungjawabkan sebelum perubahan parity berikutnya.  
**Status:** Audit berbasis evidence publik, bukan klaim bahwa aturan server asli telah direkonstruksi sempurna.

## Cara membaca matrix

Matrix ini membedakan **permukaan pengalaman** dari **formula server tersembunyi**. Evidence resmi atau visual langsung dapat menetapkan bahwa layar, tombol, resource, atau transisi pernah terlihat. Evidence tersebut tidak otomatis menetapkan koefisien, cooldown, matchmaking, atau payout. Setiap baris mencantumkan sumber dengan kelas berikut: **A** berarti official direct, **B** berarti direct visual recording, **C** berarti public secondary/version history, **D** berarti community report, dan **E** berarti recovery atau implementasi inferred.

> **Aturan parity:** State dan urutan boleh ditiru ketika didukung evidence. Formula numerik hanya boleh diubah bila ada output primer yang cukup; selain itu harus tetap configurable, versioned, dan diberi label `RECOVERY_INFERRED` atau `*_INFERRED`.

## 4. Highest-value deviations confirmed by the audit

| Priority | Confirmed deviation | Why it matters | Safe change boundary |
|---:|---|---|---|
| 1 | Player weekly cycle is compressed into one `advanceWeek` action that automatically plays a match, while the direct walkthrough presents weekly update/training result, match, EXP allocation, and league table as visibly separate screens.[3] | This is the central reason the Discord bot feels unlike the original even when domain fields exist. | Split the Discord presentation into home → weekly update → match result → EXP allocation → standings. Keep formula code unchanged initially. |
| 2 | Player/Coach are still opened through grouped slash commands and have only shallow components; the original uses persistent tab-like navigation.[3] [4] | Typing friction prevents the user from experiencing the intended loop. | Add one entry command/menu and mode-specific buttons/selects; retain grouped commands as fallback/admin surface. |
| 3 | Versus public assignment in the live adapter creates a day-based group/season immediately, while the standalone queue matcher is not the path used by `ensurePublicVersusAssignment`. | The system-managed concept is correct, but the actual production path is inconsistent and not a verified matchmaking model. | Consolidate assignment service, persist ticket status, group lock, assignment ID, and TTL; keep policy inferred. |
| 4 | Versus maintenance settles expired market listings but does not automatically process expired scheduled rounds. | The original surface visibly depends on countdown/scheduled competition; manual `/versus-round` is not game-like. | Add idempotent round job processing with one group lock and notification/outcome persistence. |
| 5 | Component interactions are deferred by `index.ts` and then deferred again by `handleComponent`. | Real button flow may produce an interaction failure independent of gameplay correctness. | Make component handler defer only when neither `replied` nor `deferred`; add adapter test. |
| 6 | Match result model lacks some visible Player fields such as MVP/audience/shots/possession/corners, although Versus has richer telemetry. | Output does not look like the observed result screen. | Extend result presentation with optional fields; do not fabricate values where no safe domain source exists. |
| 7 | Player schema lacks explicit Diamonds/Fans/value and visible onboarding contract receipt. | The top-level screen and event economy feel unlike the original. | Add nullable/versioned display state only with clear provenance; avoid unsupported mutations. |
| 8 | Coach tactic counter chain is only community evidence and not enforced. | Enforcing it as fact could make gameplay less rather than more accurate. | Expose tactics and an optional community hint; keep actual effect in inferred ruleset. |

## 5. Formula and implementation boundary

The following values are **not verified as original formulas** and must remain versioned/configurable: Player energy and HP costs, hourly/weekly recovery, match goal chance, opponent strength, EXP ranges, injury chance/duration, trainer ratio/cost, trick energy/premium acceleration, retirement threshold details, Coach approval/board thresholds, Versus MMR/rating window, group capacity, round duration, formation/tactic multipliers, lineup condition drain, auction price curve/increment/duration, Scout effects, Sponsor payout, and season reward amounts.

The following are safe parity targets because they concern visible state shape or engineering safety rather than hidden coefficients: mode separation, menu/button navigation, onboarding screens, weekly state cards, last/next fixture visibility, post-match EXP allocation, injury/treatment status, formation/roster screen, Match Preview, countdown display, locked roster snapshot, result statistics when available, reward receipts, outbid release ledger, idempotent settlement, and deterministic replay.
